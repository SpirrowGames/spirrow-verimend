# Verimend 設計メモ

2026-08-28 の設計セッションの決定事項。

## 位置づけ

- 新規プロダクト（Magickit への組み込みではなく独立サービス）。理由: 長時間バッチというライフサイクルが Magickit のリクエスト・レスポンス型 MCP ツールと不一致。スケジューラ / チェックポイント / 実行履歴という独自の関心事を持つ
- Magickit 側には薄いトリガー/照会ツールのみ追加予定（`run_reconciliation` / `get_reconciliation_status` 程度、実体は Verimend へ委譲）
- service_health の監視対象に追加する

## パイプライン

| ステージ | 手段 | 備考 |
|---|---|---|
| 実態収集 | 決定的スクリプト | コード・MCPツール定義・設定・DBスキーマ・service_health。LLM 不使用 |
| クレーム抽出 | LLM (27B) | ドキュメント → 原子的主張のリスト（出典アンカー付き） |
| 照合 | LLM (27B) + 検索 | クレーム単位で実態スニペットと突き合わせ。verified / stale / unverifiable |
| 修正 | LLM (27B) → PR | stale のみパッチ草案。1クロール = 1PR。diff は「決定的検証済み」「LLM判定」でセクション分け |
| エスカレーション | Conclair chatroom | unverifiable・大規模乖離は人間判断へ |

## LLM 運用

- Qwen3.8-27B（4bit 量子化）を Lexora の新スロットとして GPU 推論サーバー（VRAM 32GB）に配備
- `max_model_len` は 64K〜128K に制限（262K フルは VRAM と実効 recall の両面で当面使わない。1M 拡張はホスト版 YaRN の話でローカル対象外）
- hybrid attention (Gated DeltaNet 48/64層) の vLLM 安定性は要実機検証 — **現時点で最大の不確定要素**
- 導入手順: 既存モデルと別ポートで並走 → 照合タスク数十件サンプルで精度確認 → 切り替え判断
- 長距離 recall は未検証のため、照合対象は必ず検索で絞ってから渡す

## 自動適用の境界

- 自動適用可: リンク切れ、バージョン番号・コマンド名・パラメータ名の不一致など、**決定的チェックで機械的に裏が取れるもの**のみ
- PR 必須: LLM の判断を含む書き換えすべて（設計意図との整合など）
- ルーティング基準は LLM の自己申告 confidence ではなく**検証手段の種類**
- PR のマージ率・修正率を精度メトリクスとして計測し、自動化範囲拡大の判断材料にする
